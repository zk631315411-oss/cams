# CAMS V6 到 V7 研发总结

## 一、迁移目标

V6 已验证了“教材切片 -> 题目检索 -> 证据绑定 -> 解析生成”的基本可行性，但正式生产长期受句卡粒度、中文单语召回、OCR 派生文本、实验脚本耦合和工作台数据结构影响。V7 的核心任务不是换一套界面，而是重建一条可以回到教材原文、支持中英复核、能冻结版本并按题审计的内容生产链。

最终形成的主线是：以英文教材原文为切分和复核锚点，以中文内容服务教研阅读，通过冻结的双语 `unit_id` 连接题目、选项、证据、解析和页码。

## 二、V6 阶段沉淀

V6 主要完成了以下探索：

- 将教材拆为 `v6s_N*` 句卡并用于中文检索。
- 试验题目与句卡、知识图谱、考点之间的绑定。
- 形成四角色法、Weknora/RAG、新题解析和旧工作台等多个原型。
- 验证解析生成、题目展示、教材对照和教研操作的产品方向。

V6 的价值是验证路线，而非为 V7 提供可直接继承的正式证据。其主要问题是：句卡常常过窄或缺少结构上下文；中文译文和英文概念可能错位；OCR 和页码容易产生二次误差；多个试验目录之间缺少稳定契约；界面、运行目录与内容产物耦合较重。

因此 V6 被整体归档到 `v6_归档/`，保留追溯价值，但停止承担正式运行责任。

## 三、V7 的关键重构

### 1. 教材底座：从中文句卡转为双语知识单元

V7 以中英文 PDF、MinerU 中英文 Markdown、页码回填和页级对齐数据为源，最终冻结 4,973 个知识单元：

- 4,702 个可直接引用单元；
- 271 个父级或上下文单元；
- 10 个排除或待复核项；
- 无重复 `unit_id`，无重复直接句子 ID。

正式锚点统一为 `v7u_N*`。英文 `en_quote` 是原文复核依据，中文 `knowledge_zh` 和上下文用于检索与教研展示，页码和章节路径随单元保存。

### 2. 检索底座：从单路召回转为多路候选池

V7 建立了中文 BM25、英文 BM25、BGE 向量检索，并可叠加 P5 术语别名和知识图谱扩展。KG/P5 只负责扩大候选范围，不能直接充当教材证据；所有最终引用必须回到真实 `unit_id` 与教材原文。

### 3. 题库底座：统一结构化与章节映射

395 道题经过 Phase 3.5 标准化，形成稳定题目 ID、题型、选项、章节映射和质量报告。OCR 选项边界、中英答案冲突和参考解析错位被显式记录，不再静默修补。

### 4. 判断与解析分离

V7 将 Phase 4 拆成两个职责明确的环节：

```text
题目 + 多路候选教材 unit
  -> 盲判：不读取参考答案，独立判断选项并绑定证据
  -> 后置审计：比较 AI 判断与中英参考答案
  -> 解析：锁定盲判结论，撰写考点、核心解析、错误项和易错提醒
  -> 机械复核与深度质量复核
  -> 人工终审
  -> 软件小节 Markdown / DOCX
```

这一设计避免了“知道答案后反向寻找理由”。参考答案只用于后置冲突审计，不能进入盲判提示词。

### 5. 证据与文字生成分离

LLM 负责语义判断和解析文字，本地代码负责可验证字段：真实 `unit_id`、原文引用、页码、选项映射、答案格式和导出结构。候选池外引用、幻觉 ID、字段矛盾和引用格式问题由本地门禁处理。

### 6. 从工作台展示转向软件交付

研发中建设过多个前端与审核原型，但最终交付重心已经转为稳定内容资产：逐题 JSON、逐题 Markdown、63 个软件小节文件和双语 DOCX。前端经验保留为产品设计参考，不再定义正式数据来源。

## 四、已交付成果

- 4,973 个冻结双语教材知识单元。
- 395 道结构化 V7 题目及章节映射。
- 395 份盲判、选项级分析和候选证据 JSON。
- 395 份教研解析 Markdown 母版。
- 63 个软件小节 Markdown、63 个软件小节 DOCX、63 个双语 DOCX。
- 新教材新题库 SOP、新题增量 SOP、运营使用指南及对应 DOCX。
- V7 知识图谱：59 章、983 点、8,632 边及 P5 alias，用作检索增强。

## 五、研发中确认的有效原则

1. 教材原文和页码是最终依据，检索结果、KG 关系和参考答案都只是辅助信息。
2. 英文负责概念边界和原文锚定，中文负责教研阅读与交付表达。
3. 判断、解析、审核、发布必须分层，不能由一次模型调用包办。
4. 自动校验只证明结构合规，不能代替语义蕴含和人工裁决。
5. 题目答案冲突、教材证据不足、翻译歧义和跨章证据必须显式保留状态。
6. 正式母版应不可变发布；新一轮修改应生成新版本或新发布包，不能覆盖历史结论。

## 六、主要教训

- 先做界面、后定数据契约，会反复返工；正式产品应先冻结内容契约。
- 以“运行目录最新文件”作为事实来源会导致旧结果混入，必须使用发布清单和输入哈希。
- 只检查 `unit_id` 是否存在远远不够，还必须检查主语、条件、时间节点和场景是否真的支持选项。
- 自动报告具有时点性。内容修改后必须重跑报告，否则“曾经通过/曾经失败”都不能代表当前版本。
- 测试跑批和正式输出放在同一目录会增加误用概率，应按 `tests/`、`runs/`、`release/` 分层，并让发布器只读批准清单。

## 七、后续工作

优先级最高的不是继续扩建前端，而是：

1. 将当前终审后的 395 题生成带哈希的不可变正式发布清单。
2. 对当前文件重跑机械检查与必要的深度质量检查，替换过期报告。
3. 将 `codex_status=reviewable` 与 `human_status=approved` 接入正式发布双门禁。
4. 后续新增题按增量 SOP 处理，不重跑无关教材底座。
5. Phase 5-8 考点物化如继续实施，应只从当前 V7 证据边出发，不继承 V6 考点绑定。
