# s2：知识图谱扩展研究

s2 是知识图谱扩展研究层。它在 s1 直接单元召回之后启动，研究如何利用知识图谱扩展候选上下文，同时保持精确性和可观察性。

本阶段尚未定稿。当前脚本是 v0 实现版本，仅用于检查；扩展逻辑在作为默认检索流水线使用前仍需优化。

## 定位

来自前序阶段的输入：

- s0 构建检索头。
- s1 运行直接单元召回并产生单元种子。

s2 随后将这些单元种子连接到知识图谱：

```text
s1 直接 unit_id 种子
  -> unit_id 到 core_point
  -> 同一 core_point 下的单元
  -> 关联 core_point 边
  -> 候选知识图谱扩展单元（含可读路径）
```

输出目标：

- s3，直接召回文本和知识图谱扩展文本将在那里重排序、组织和渲染为 LLM 可读的召回上下文。

## 当前契约

s2 应保留以下维度，而非过早合并：

- `question_id`
- 检索头：`stem`、`option_A`、`option_B`……
- s1 来源路线
- 直接种子单元 ID
- 知识图谱扩展来源
- 知识图谱路径
- 关系类型、边范围和方向（当使用边时）

每个知识图谱新增单元必须保留路径。路径应足够可读，以便后续 s3 渲染，例如：

```text
seed_unit -> seed_core_point --relation/scope/direction--> target_core_point -> target_unit
```

## 来自 s1 的推荐种子策略

当前 s1 的发现是：

- `s0a` 仅用于诊断，因为破坏性太强。
- `s0b` 可增加有用的别名/定义单元，但可能引入定义噪音。
- `s0c` 是最稳定的增强路线。
- 后续阶段应使用 `baseline union s0c` 作为主候选池。
- `s0b` 新增单元可作为可观察补充保留，而非基线证据的默认替代。

因此，下一版 s2 设计至少应支持：

- `baseline_union_s0c`：主种子池。
- `s0b_added_observation`：可选补充，用于检查。
- `s0a_diagnostic`：仅可选诊断分支。

当前 v0 脚本尚未完全实现此策略。

## 待研究的扩展层

s2 应逐层测试知识图谱扩展：

- `direct_seed`：保留 s1 直接单元作为根节点。
- `same_core_point`：在种子核心点下添加兄弟单元。
- `related_core_point_edge`：遍历核心点之间可观察的知识图谱边。
- `section_context`：可选同章节上下文；在测量噪音前默认应关闭。

尚待解决的重要设计问题：

- 多少种子单元应进入知识图谱扩展？
- 选项头和题干头是否应有不同的知识图谱预算？
- 边方向是否应影响遍历，还是仅影响打分？
- 哪些关系类型足够安全可用于自动扩展？
- 跨章节边是否应默认禁用？
- 知识图谱输出是否应现在打分，还是仅标注留待 s3 重排序？
- 到达同一单元的重复路径应如何保留或汇总？

## 边界

s2 不：

- 运行 BGE 或 BM25 检索；
- 调用 LLM；
- 判定选项答案；
- 编写面向学员的解析；
- 将知识图谱扩展单元视为最终证据。

s2 只为后续阶段创建候选上下文。

## 现有 v0 脚本

脚本：

```powershell
python tests/stepwise_retrieval/s2/s2_kg_expansion.py --question-id v7_q_000009 --experiment all
```

当前限制：

- 仅支持较早的 `s0a` 和 `s0b` 实验路线；
- 未实现 `baseline union s0c`；
- 生成的 Markdown 需要清理以提高中文可读性；
- 在确定最佳策略前使用固定预算扩展；
- 应视为检查原型，而非最终的 s2 工作流。

在审查并更新扩展策略之前，不要将此脚本作为默认 s2 实验重新运行。

## 研究指标

s2 输出最终应报告：

- 直接种子单元数；
- 知识图谱新增单元数；
- 总单元数；
- 覆盖的核心点数；
- 覆盖的章节数；
- 关系和边范围分布；
- 跨章节扩展比例；
- 平均每个种子新增单元数；
- 重复单元比例；
- 未映射到知识图谱核心点的种子单元；
- 具有多条支持路径的热门单元。
