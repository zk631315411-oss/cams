# Grounded Card Codebook v1

> **状态**：本 CODEBOOK 归纳的 25 种节点类型（E1-E8, P1-P10, X1-X7）已纳入 P7A schema，作为 `flow_node.node_type` 的正式取值。`node_category` 字段（entry/process/exit/auxiliary）对应入口/处理/出口/辅助四大类。

## Card 核心定义

```text
card = 可考情境/线索 + 考生应完成的识别、判断、归因或应对 + 可检验结论/应对要求
```

更严格地说：

> Card 是由当前 section 的 unit 证据支持的一段局部考试推理结构。它从可考情境、异常线索、业务事件、监管要求或对象进入开始，经由识别、判断、归因、分类、控制匹配或应对动作，形成风险判断、红旗结论、控制要求、流程产物、状态变化、交接或持续义务。业务流程卡是 card 的一种，但不是唯一类型；案例推理、红旗识别、风险归因和控制匹配，只要形成可考推理链，也可以成卡。

## 入口类型

| 代码 | 类型 | 定义 | 例子 |
|---|---|---|---|
| E1 | 事件/信号 | 可定位的业务事件启动处理 | 系统生成告警、收到执法请求 |
| E2 | 对象进入 | 某类客户、交易、账户或载体进入处理范围 | 高风险客户申请准入、SPV/PIV 客户 |
| E3 | 状态/阈值 | 已观察状态或阈值结果要求处理 | 剩余风险超容忍度、风险评级升高 |
| E4 | 上游交接 | 上一局部流程的输出成为本流程输入 | L1 升级至 L2、SAR 已提交后处置账户 |
| E5 | 时间/周期 | 固定周期或期限启动/约束处理 | KYC refresh 到期、SAR 提交期限 |
| E6 | 变化/例外 | 环境变化、异常或信息缺口启动调整 | 监管变化、异常交易、缺少关键资料 |
| E7 | 外部指令/义务 | 法律、监管或执法要求启动处理 | 执法请求、报告义务、账户保持开放指令 |
| E8 | 决定/发现 | 前一判断本身触发后续义务 | 决定不提交 SAR、发现控制缺陷 |

## 处理类型

**处理 = 考生应该完成的识别、判断、归因或应对动作。**

| 代码 | 类型 | 定义 | 例子 |
|---|---|---|---|
| P1 | 评估/分类 | 识别风险信号或异常模式，使用标准形成分类、适宜性或有效性结论 | 识别红旗信号、标记高风险模式、评估控制有效性、风险分类 |
| P2 | 执行/转换 | 对业务对象实施动作或应对措施，使其状态发生变化 | 执行 EDD、提交 SAR、加强监控、提高审查频率 |
| P3 | 条件分支/路由 | 根据条件选择关闭、升级、继续、拒绝或其他路径 | 可疑则升级、不可疑则关闭、高风险则进入 EDD |
| P4 | 信息收集/产物装配 | 汇集信息或部件，形成调查基础或正式产物 | 收集客户资料、装配 SAR 叙述、整理证据包 |
| P5 | 协调/委托 | 多角色、多部门或前后台协同完成任务 | 跨部门协调、委托一线获取信息、协调执法响应 |
| P6 | 反馈/补救 | 根据缺陷、复核问题或结果返回修改、补充研究或重新设计 | 补充调查、修改控制设计、纠正操作错误 |
| P7 | 周期/持续监控 | 按周期重复，或持续观察直到新事件再次触发 | KYC refresh、持续交易监控、定期复核 |
| P8 | 约束型行动 | 动作必须同时满足保密、禁止泄密、法律、相称性等约束 | 受约束的外联、保密前提下的信息披露 |
| P9 | 计划/治理 | 将风险处置组织为责任人、期限、措施、复核和升级机制 | 编制行动计划、设定治理框架 |
| P10 | 充分性/停止判断 | 判断证据是否足以支持结论并决定继续或停止研究 | 判断调查是否充分、决定是否停止研究 |

处理类型可以组合。例如执法请求响应是 `P1 + P5 + P8`，控制缺陷补救是 `P1 + P6`，风险信号识别是 `P1` 的识别阶段。类型不是必须互斥的 card 标签。

## 出口类型

| 代码 | 类型 | 定义 | 例子 |
|---|---|---|---|
| X1 | 分类/判断 | 形成可疑性、风险、有效性或适宜性结论 | 高风险、控制无效、活动可疑 |
| X2 | 产物/记录 | 形成可识别、可保存或可提交的对象 | SAR、行动计划、理由档案、沟通记录 |
| X3 | 状态变化 | 业务对象进入新的稳定状态 | 账户关闭、支付冻结、客户被拒绝 |
| X4 | 交接/升级 | 转交下一角色、层级或局部流程 | 升级 L2、转 MLRO、进入 EDD |
| X5 | 配置/控制变化 | 规则、阈值、场景、控制或培训被修改 | 新阈值、重设 QC、补充培训 |
| X6 | 终止/无需继续 | 当前局部目标结束且无进一步动作 | 误报告警关闭、解释充分后停止升级 |
| X7 | 持续义务/受控继续 | 进入持续监控、周期复核或受限制关系 | 保持账户并强化监控 |

## 从材料中归纳出的 Card 原型

这些原型是入口、处理和出口的常见组合，不是先验强制分类：

| 原型 | 典型结构 |
|---|---|
| 闸门/准入 | 对象进入 -> 适宜性或风险判断 -> 拒绝/进入下一流程 |
| 评估/分类 | 状态或对象 -> 多标准评估 -> 分类/判断 |
| 执行/产物 | 任务启动 -> 收集、加工、装配 -> 正式产物 |
| 分支/处置 | 事件或发现 -> 条件判断 -> 不同状态变化或动作 |
| 升级/交接 | 信号 -> 本级处理 -> 关闭或交给下一层级 |
| 反馈/补救 | 缺陷或复核问题 -> 根因、补充、修改 -> 修复后的控制/材料 |
| 周期/监控 | 周期或持续信号 -> 复核/监控 -> 更新状态或再次触发 |
| 计划/治理 | 超容忍风险 -> 设计措施、责任、期限和升级 -> 行动计划 |
| 受约束响应 | 外部请求或信息需求 -> 协调行动并满足禁止/法律约束 -> 合规响应/记录 |
| 充分性/停止 | 调查进行中 -> 判断证据与过程是否可辩护 -> 继续或停止 |
| 案例推理 | 案例情境/异常线索 -> 识别作案机制、红旗或风险来源 -> 风险结论/控制要求 |
| 红旗识别 | 异常行为或模式 -> 判断是否构成 red flag / high-risk pattern -> 标记高风险或进入加强监控 |

## 成卡规则

一段材料成为 card，必须同时满足：

1. **入口可识别**：原文明确给出事件、对象、状态、请求、周期、变化或上游交接；结构性 `start` 不得替代业务入口。
2. **存在认知或业务处理**：至少有一个识别、判断、归因、分类、控制匹配、应对动作、分支、协调、反馈或停止判断。
3. **出口可观察**：至少形成分类、产物、状态变化、交接、配置变化、终止或持续义务。
4. **关系可举证**：入口到处理、处理到出口均能绑定当前 section unit；不能只凭常识补链。
5. **局部目标单一**：整张卡围绕一次可命名的可考目标或业务目的，而不是覆盖完整宏观生命周期。

## 不成卡规则

以下内容默认留在普通 KG 或证据层：

- 术语定义、背景和单个事实。
- 只有风险、好处、影响或政策价值，且不能形成“线索 -> 识别/判断/归因 -> 结论/应对要求”的可考推理链。
- 红旗或标准列表未与某个判断/处置动作相连。
- 只有“应降低风险、提高效率”等抽象目标，没有可观察业务结果。
- 外部主体的工作方式与机构侧没有判断、响应、交接或结果关系。
- 依靠 CP 顺序、主题顺序或常识才能补出入口/出口的伪流程。
- 案例叙事本身不自动成卡；但如果案例提供了可考线索、风险机制、红旗识别和应对要求，可以形成案例推理卡。

## 拆卡规则

出现以下任一情况，应优先考虑拆卡：

1. 某个中间结果可以独立保存、审查或被下游消费。
2. 一个出口明确成为下一阶段入口。
3. 不同阶段有不同责任人、目标和判断标准。
4. 某一分支形成独立的后续义务，而不是当前动作的简单结果。
5. 合并后必须使用大量 `functional_dependency` 才能维持流程连续性。

不得仅因教材列出多个项目就拆卡。并列标准、输入字段和控制要求通常属于同一处理节点群。

## 对现有 P7C 的含义

1. `card_nature` 不应作为第一轮识别 card 的入口；应先确定状态转换，再做派生分类。
2. `start` 和 `end` 不再是为满足 schema 添加的结构节点。入口和出口都必须表达业务语义。
3. `risk_indicator` 不能天然成卡；只有红旗进入明确评估或处置并产生出口时才成卡。
4. `judgement_card` 合法，但必须有判断对象、标准/过程和明确结论/路由。
5. `CH49-S16` 类型的政策副作用应进入 evidence-only，而不是为了召回率强行生成 3 节点 card。
6. `CH47-S06` 类型的多级流程应沿稳定出口/交接点拆分，而不是做一张 25 节点宏卡。
