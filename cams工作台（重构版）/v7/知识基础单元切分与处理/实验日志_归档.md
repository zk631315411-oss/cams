## 2026-07-02 Update: DS API Decision Manifest 固化

当前子代理试跑已经证明“规则定位 + 语义分组 + 脚本回填原文”的方向可行，但子代理产物缺少正式 LLM 调用层的审计信息。下一阶段应先固化 prompt、模型、input hash 和 decision manifest，再把子代理替换为 DeepSeek API。

### 为什么先固化 manifest

如果只把子代理换成 DS API，但不保存 prompt/model/input hash/raw response，那么后续仍然无法回答这些问题：

- 某个 `sentence_ids` 分组到底由哪个 prompt 产生。
- 输入 batch 是否在重跑前后发生过变化。
- 模型返回的原始内容是什么，解析器有没有修复 JSON。
- 同一个 request 是否可以按同一 prompt/model 复跑。

因此从本阶段开始，正式 DS 跑批必须留下三层产物：

1. **固定 prompt**
   - 文件：`prompts/v7_unit_split_v1.md`
   - 规则：LLM 只能输出 `sentence_ids` 分组、`unit_type`、`knowledge_hint_en`、`reason`、`risk_flags`。
   - 禁止：LLM 直接输出或改写 `en_quote`。

2. **run manifest**
   - 脚本：`scripts/run_ds_unit_grouping_batch.py`
   - 输出：`work/base_units/llm_runs/<run_slug>/run_manifest.json`
   - 记录：
     - provider/model/base_url/temperature/max_tokens/json_mode
     - prompt file 与 `prompt_sha256`
     - batch file 与 `batch_sha256`
     - 每个 request 的 `input_sha256`
     - 每个实际 message 的 `message_sha256`
     - raw response 路径与 `raw_response_sha256`
     - API usage、状态、错误信息

3. **decision JSONL**
   - 输出仍然进入 `work/base_units/llm_batches/*_decisions*.jsonl`
   - 每行除原有字段外，增加 `_meta`：
     - `provider`
     - `model`
     - `prompt_sha256`
     - `input_sha256`
     - `message_sha256`
     - `raw_response_path`
     - `raw_response_sha256`
     - `status`

### 替换子代理的节奏

建议不要立刻全书 DS 跑批，而是按以下顺序替换：

1. 选一个已由子代理跑过的小批次，例如 `Other AFC regulations that impact organizations` 的 18 条。
2. 用 DS runner 跑同一个 batch，生成 DS decisions、raw responses、run manifest。
3. 用 provenance validator 校验。
4. 用现有 materializer + combined builder 物化。
5. 将 DS 结果与子代理结果对比：
   - direct/review 数量是否接近。
   - 关键残句是否仍进 review。
   - 大段是否被过度合并。
   - 单句高密度法规条款是否被误拆。
6. 小批质量通过后，再按章节顺序用 DS runner 替代子代理。

### 2026-07-02 实测结论：DeepSeek Chat 可先作为正式分组模型

本轮将 DS runner 的默认输出预算从 `4096` 调整为 `8192`，并增加 `timeout_seconds=120` 的显式超时记录。实际测试命令中为避免单批挂死，使用 `--timeout-seconds 60 --retries 2`。

已完成两批小规模 DS Chat 测试：

| batch | rows | model | max_tokens | decision 校验 | 物化结果 | combined 审计 |
|---|---:|---|---:|---|---|---|
| `other_afc_regulations_impact_organizations.offset000_limit020` | 18 | `deepseek-chat` | 8192 | issues=0, provenance_issues=0 | direct=46, review=4 | audit issues=0 |
| `other_laws_regulations_impact_organizations.offset000_limit020` | 20 | `deepseek-chat` | 8192 | issues=0, provenance_issues=0 | direct=49, review=4 | audit issues=0；combined 后 direct=58, parent/context=2 |

质量观察：

- `deepseek-chat` 在反腐、制裁、数据隐私、DORA、GDPR 等不同主题上均能稳定返回合法 JSON，暂未需要切换 `deepseek-v4-pro`。
- 与子代理试跑相比，DS Chat 通常切得更细。例如 FCPA 段落被拆成“生效事实 / 禁止向外国官员付款 / 域外适用 / 外国勒索防范修正案 / facilitation payment 例外”，更适合后续题目证据绑定。
- 跨块残句没有被放入 direct evidence，而是被 review gate 拦截。例如 `For large companies and public`、`Regulations.`、`Additionally, critical ICT third-party service` 等仍进入 `review_items`。
- 当前中文侧仍保持 pending：`knowledge_zh`、`zh_display_text`、`zh_search_text` 不由本阶段伪造，避免把整段中文误当精准证据。

暂定策略：

1. 后续小批量继续优先使用 `deepseek-chat`，配置固定为 `temperature=0`、`json_mode=true`、`max_tokens=8192`。
2. 只有当某批出现连续 malformed、timeout 后仍失败、或人工抽查发现切分质量明显退化时，才切换 `deepseek-v4-pro` 重跑该批。
3. 在全书正式批跑前，仍保持 draft-only：不冻结正式 `v7u_N*`，不进入题目绑定。
