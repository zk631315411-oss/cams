## 2. 项目目标与正式流程

项目把一道 CAMS 题目从题源接收推进到可追溯发布。它不仅保存最终答案，还必须回答：题面是哪一版、证据从哪里来、Codex 修改了什么、教研确认了哪一版、发布包绑定了哪些版本。

```text
接收整理 -> 重复检查 -> 证据研究 -> 证据确认
         -> 正式解析 -> 最终核验 -> 教研批准 -> 发布
```

正式阶段由 `workflow.json` 表达，Codex 当前在做什么由 `task_state.json` 表达。任务完成不等于正式阶段自动通过，二者不可重新合并为同一个状态字段。

DeepSeek 不是正式流程节点。`request_ds_opinion` 仅在教研明确同意时提供独立第二意见，成功或失败都不推进工作流。旧代码中的 `ds_draft.json`、`write_ds_draft` 和 `write_codex_review` 属于 Deprecated 兼容能力，不是当前正式主线；待接手开发者确认无外部调用者后删除代码入口，但保留历史数据的读取与追溯。

## 3. 架构与不可破坏的边界

```text
教研网页 -> HTTP API ----\
                         -> storage.py -> 题目档案 / 审计 / 发布包
Codex GUI -> stdio MCP --/
                  |
                  -> retrieval -> 冻结教材 / 向量索引 / KG / 术语表 / BGE-M3
```

- `frontend/`：原生 HTML、CSS、JavaScript。负责题目/PDF 分屏、证据确认、解析批注和教研决定；不得直接写 `data/`。
- `backend/api.py`：网页的 HTTP 入口，同时提供静态文件、教材页面渲染、题目详情、分页证据和人工动作接口。
- `backend/mcp_server.py`：Codex 的 stdio MCP 入口。当前版本 `2.1.0`，暴露 19 个工具。
- `backend/storage.py`：唯一正式写入层，负责原子 JSON 写入、JSONL 追加、题号锁、题目锁、乐观版本检查、审计、工作流门禁及发布构建。新增 API 或 MCP 写操作时必须经过这里。
- `backend/retrieval/`：检索资产加载及业务管线。`service.py` 区分一般检索与题目检索；`pipeline.py` 保留 V7 的 BGE、BM25、RRF、KG、P5 和选项补充参数；`assets.py` 负责路径解析、清单校验及模型懒加载。
- `backend/textbook.py`：PDF 信息、页渲染和原文位置匹配，供网页的中英文/双语教材阅读器使用。
- `backend/drafting/deepseek.py`：可选 DeepSeek 第二意见。API Key 位于用户本机配置目录，不进入题库、审计或备份。
- `backend/backup.py`：只备份可变数据 `data/questions`、`data/control` 和 `releases`；当前没有恢复实现。
- `backend/review/`：目前只有包初始化文件，正式审核和发布规则实际仍在 `storage.py`。
- `data/infrastructure/`：冻结教材、索引、KG、P5 术语资产。日常 API/MCP 只读；维护资产时必须同步版本、清单与哈希。
- `runtime/models/bge-m3/`：本地模型文件，约 2.28 GB。它不等同于可用 Python 推理环境。
- `releases/`：不可变发布快照；同一 `release_id` 不允许覆盖。

必须保持以下约束：

1. 同一题同一时间只允许一个写操作，不同题可并行。
2. MCP 写入前先 `read_question`，再提交当前 `expected_question_version` 与 `expected_archive_revision`。
3. `question.version` 只在题面内容变化时递增；`archive_revision` 在题目档案写入时递增，用于阻止旧页面或旧 MCP 结果覆盖新数据。
4. 修改题干、选项或答案后，旧证据确认、解析、核验和批准必须失效，但历史记录不得删除。
5. 发布只接受题面、证据确认、正式解析、最终核验和人工批准版本完全一致的记录。
6. 教研确认证据、提交解析批注、标记润色完成及最终批准均由网页完成；Codex 负责研究、整理、解析版本和最终核验，不能代替教研作正式决定。

## 4. 题目档案与版本权威性

每道题位于 `data/questions/<question_id>/`。文件按流程逐步产生，并非每题都同时具备全部文件。

| 文件 | 作用 |
| --- | --- |
| `source/` | 题源原件、附件和接收信息 |
| `question.json` | 当前有效题面；其中旧 `status` 仅用于兼容，不是 V2 正式阶段权威字段 |
| `workflow.json` | V2 正式阶段、处置状态和当前绑定版本，正式流程的权威记录 |
| `task_state.json` | 当前任务状态、执行者、等待对象和下一步 |
| `task_history.jsonl` | 任务状态的追加历史 |
| `retrieval_runs.jsonl` | 每轮检索的查询、参数、渠道和原始结果 |
| `evidence_catalog.json` | 跨轮次去重的题目级证据目录，同时保留发现历史 |
| `evidence_candidates.jsonl` | Codex 提交给教研的精选候选版本 |
| `evidence_confirmation.json` | 教研确认的当前固定证据版本 |
| `analysis_versions.jsonl` | Codex 生成或修订的正式解析版本 |
| `analysis_feedback.jsonl` | 教研对解析的批注 |
| `final_checks.jsonl` | Codex 对固定题面、证据和解析版本的最终核验 |
| `decision.json` | 教研批准、退回、暂缓或不收录决定及绑定版本 |
| `audit.jsonl` | 题目级写入审计；只追加，不覆盖 |

迁移题可能保留 `evidence_review.json` 等旧流程文件。不要删除，也不要让旧文件重新成为 V2 工作流的发布依据。当前样本 `v7_q_000001` 的 `question.status=ready_for_ds` 是旧状态，真正阶段以 `workflow.json` 的 `stage=evidence_research` 为准。

临时网页选题上下文位于 `data/control/active-context.json`。它不属于题目正式版本，不增加 `archive_revision`，也不进入发布包。

## 5. Windows 开发、测试与 MCP

### 5.1 当前环境

现有环境可以运行不依赖真实 BGE 推理的单元测试和网页骨架：

```powershell
cd "D:\守正公司工作区\cams考试工作台（正式版）"
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\scripts\start-web.ps1 -Port 8765
```

浏览器地址为 `http://127.0.0.1:8765`。启动 API 时会尝试执行每日首次备份，默认写到当前用户目录下的 `CAMS考试工作台备份`。

不要把 `setup.ps1` 的成功导入检查当成检索验收。接手后必须额外执行《已知问题与后续任务》中的 BGE `encode` 和真实 `search_evidence` 命令。

### 5.2 MCP

Windows 的 stdio MCP 启动命令：

```text
command: powershell.exe
args: ["-ExecutionPolicy", "Bypass", "-File", "<正式版根目录>\\scripts\\start-mcp.ps1"]
```

正式版目录目前没有 `.codex/config.toml`。开发机现有 CAMS MCP 是登记在父项目 `D:\守正公司工作区\cams考试\.codex\config.toml` 中，并写死为本机绝对路径；它只能作为当前机器的开发配置，不能直接作为交接文件。Codex 项目级模板见 `docs/macos-project-mcp-config.example.toml`；`docs/mcp-config.example.json` 是保留的历史/其他客户端格式，不是当前 Codex 配置。

MCP 工具按职责分为：

- 读取：`list_questions`、`read_active_context`、`read_question`、`read_evidence_catalog`、`read_audit`、`search_evidence`、`retrieve_question_evidence`。
- 新题和证据：`create_question_intake`、`resolve_duplicate_check`、`register_evidence`、`curate_evidence`、`submit_evidence_candidate`。
- 解析与核验：`write_analysis_version`、`write_final_check`、`reopen_evidence`、`set_task_state`。
- 显式确认动作：`request_ds_opinion`、`update_question`、`build_release`。后三者要求 `confirmed=true` 和原因。

只读冒烟检查：

```powershell
'{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}' |
  .\.venv\Scripts\python.exe backend\mcp_server.py --workspace-root .
```

## 6. macOS M3 目标状态

目标设备是 Apple Silicon M3、macOS 14 或更高，计划固定安装到 `~/CAMS考试工作台`。当前只具备 `scripts/macos/` 源码，不能称为“解压即用”。

当前缺少：

- `runtime/python/` 中可迁移的 CPython 3.11 arm64 运行时；
- `wheelhouse/macos-arm64/`；
- `requirements-macos-arm64.lock`；
- `dist/CAMS考试工作台-macos-arm64.tar.gz` 及其 SHA-256；
- M3 上的断网检索、Codex Desktop、Gatekeeper、中文空格路径、备份恢复和完整业务流程验收记录。

`scripts/macos/build-package.command` 必须在 M3 Mac 上运行，并依赖 `CAMS_MAC_PYTHON_HOME` 指向可迁移 Python。运行时来源和制作方法目前未写明，待后续开发解决。`检查环境.command` 还引用已退出正式主线的旧 MCP 工具名，当前会误判，不能作为验收凭据。

## 7. 接手第一天建议顺序

1. 向移交方确认代码基线、公司私有仓库地址、历史材料范围、后续负责人和验收时间；尚未确认的内容不要自行推断。
2. 将正式版纳入独立版本控制或取得不可变源码快照与 SHA-256。不要把父仓库的大量历史脏工作树当作正式版基线。
3. 先只读统计 395 道题、工作流阶段和 `releases/`，对照本文件确认数据未丢失。
4. 使用现有 `.venv` 运行 27 项测试，记录 Python 和依赖版本。
5. 复现 BGE-M3 加载失败和检索 CLI 导入失败；先锁定可复现环境，再修改依赖或代码。
6. 启动网页，查看 `v7_q_000001`，从前端请求追到 `api.py`、`storage.py` 和该题目录；不要在交接原件上提交批准或构建发布。
7. 运行 MCP `tools/list` 和 `read_active_context`，确认 Codex 项目配置指向接手者自己的正式版绝对路径。
8. 在临时副本中走一遍新题建档、证据登记、证据确认、解析、核验、批准和测试发布；完成前不要声称端到端流程已验收。
9. 最后处理 macOS M3 运行时与离线包；Windows 测试不能替代 M3 验收。
