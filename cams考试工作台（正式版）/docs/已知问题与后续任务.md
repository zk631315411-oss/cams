# CAMS 正式工作台已知问题与后续任务

> 核验日期：2026-07-30。优先级反映对开发基线、真实检索和正式交付的影响，不代表负责人或截止日期；负责人、截止日期和交付承诺均待交接双方确认。

## 1. 处理口径

- **交接前必须处理**：若不处理，接手者无法确认收到的代码和数据是哪一版，存在继续开发错基线或丢失变更的风险。
- **可由接手者继续**：允许以“开发中项目”交接，但必须保留复现证据，且在修复和验收前不得宣称相关能力可用。
- **正式发布阻塞**：不阻止开发交接，但阻止称为可用成品、正式 macOS 包或端到端验收版本。

## 2. 阻塞级

### P0-1 正式版没有独立 Git 基线

**处理口径：交接前必须处理。**

现象：

```powershell
cd "D:\守正公司工作区\cams考试工作台（正式版）"
git rev-parse --is-inside-work-tree
```

当前结果为 `fatal: not a git repository`。父目录 `D:\守正公司工作区\cams考试` 虽是 Git 仓库，但正式版位于其工作树之外，且父仓库本身存在大量无关未提交变更，不能作为正式版基线。

影响：无法可靠说明交接版本、审查差异、回滚或证明两人看到同一份源码和数据。

建议：由交接双方确定公司私有仓库或不可变归档策略。至少形成基线版本号、源码清单、SHA-256 和交接记录；模型、教材、题库数据是否进入 Git LFS、Release 或网盘需单独决定。

验收条件：接手者可以从约定来源还原同一基线；`git status` 或归档清单可解释；数据和大文件的来源、版本及哈希有记录。

### P0-2 BGE-M3 在当前 Windows 依赖组合下无法加载

**处理口径：可由接手者继续；正式检索和正式发布阻塞。**

当前环境：Python 3.11.9、`sentence-transformers 3.4.1`、`transformers 4.57.6`、`torch 2.13.0`、`numpy 2.3.2`、`scikit-learn 1.9.0`。`backend/requirements.txt` 使用宽范围，没有锁定 `transformers`，因此重建环境不可复现。

复现：

```powershell
$env:CAMS_BGE_MODEL_PATH=(Resolve-Path runtime\models\bge-m3).Path
.\.venv\Scripts\python.exe -c "from sentence_transformers import SentenceTransformer; m=SentenceTransformer(r'$env:CAMS_BGE_MODEL_PATH', local_files_only=True); print(m.encode(['risk assessment']).shape)"
```

当前在 `AutoTokenizer` 加载阶段失败：

```text
AttributeError: 'NoneType' object has no attribute 'endswith'
```

真实服务同样失败：

```powershell
$env:PYTHONPATH=(Resolve-Path backend).Path
.\.venv\Scripts\python.exe -c "from retrieval.service import search_evidence; print(search_evidence('.', 'risk assessment', 1))"
```

最终由 `backend/retrieval/assets.py` 抛出 `AssetError: 无法离线加载 BGE 模型`。模型文件存在不代表依赖组合可用。

影响：`search_evidence`、`retrieve_question_evidence`、正式证据整理和 BGE 重复候选不可用；现有 27 项测试使用测试替身，没有覆盖真实模型加载。

建议：在隔离环境中确定 BGE-M3 可加载且可 `encode` 的精确版本组合，补齐模型所需 tokenizer 文件或调整兼容版本；随后生成锁文件。不要直接覆盖当前 `.venv`，先保留失败环境用于对照。

验收条件：断网条件下成功加载 `runtime/models/bge-m3`，完成一次非空 `encode`，再对真实冻结资产分别完成一般检索和题目检索；结果包含教材版本、`unit_id`、页码和检索参数快照。该测试应进入自动环境检查。

## 3. 高优先级

### P1-1 检索 CLI 无法按文件路径直接运行

**处理口径：可由接手者继续。**

复现：

```powershell
.\.venv\Scripts\python.exe backend\retrieval\cli.py search --query "risk assessment" --top-k 1
```

当前报错：

```text
ModuleNotFoundError: No module named 'storage'
```

证据位置：`backend/retrieval/cli.py` 同时使用顶层 `from storage import WorkspaceStore` 和相对导入 `.service`，直接脚本模式与包模式未统一。

影响：README 之外的开发者 CLI 调试入口不可用，容易把导入失败误判为检索资产失败。

建议：统一为可执行模块入口，例如 `python -m backend.retrieval.cli`，并统一包内导入；同时补充 CLI 冒烟测试。

验收条件：在仓库根目录通过文档规定的唯一命令执行 `search` 和 `question`，`--workspace-root`、环境变量和默认根目录三种路径解析均有测试。

### P1-2 macOS 环境检查仍搜索旧 MCP 工具名

**处理口径：可由接手者继续；macOS 正式发布阻塞。**

证据：`scripts/macos/检查环境.command` 使用：

```bash
... backend/mcp_server.py ... | grep -q 'write_codex_review'
```

当前 MCP V2 正式工具已改为 `submit_evidence_candidate`、`write_analysis_version`、`write_final_check` 等；`tools/list` 中没有 `write_codex_review`。

影响：即使其他环境正确，macOS 检查脚本也会误报失败；后续真实检索命令不会执行。

建议：改为核验 V2 的关键只读与写入工具集合，并校验 MCP 版本；不要只 grep 一个字符串。

验收条件：M3 上 `tools/list` 返回 19 个当前工具，至少包含 `read_active_context`、`retrieve_question_evidence`、`submit_evidence_candidate`、`write_analysis_version`、`write_final_check` 和 `build_release`，且不依赖旧工具名。

### P1-3 macOS 正式交付资源尚未生成

**处理口径：可由接手者继续；macOS 正式发布阻塞。**

当前缺少：

```text
runtime/python/
wheelhouse/macos-arm64/
requirements-macos-arm64.lock
dist/CAMS考试工作台-macos-arm64.tar.gz
```

模型 `runtime/models/bge-m3/` 已存在。`scripts/macos/build-package.command` 要求在 M3 上提供 `CAMS_MAC_PYTHON_HOME` 指向可迁移 CPython 3.11 arm64，但文档未说明该运行时的来源、制作和重定位验证方式。

影响：不能断网安装、不能运行项目级 MCP，也不能称为“解压即用 macOS 包”。Windows 无法替代 arm64 构建与验证。

建议：先修复并锁定 BGE 依赖，再在目标 M3 构建。记录 Python 来源、许可证、架构、依赖锁、wheelhouse 和文件哈希。

验收条件：在干净的 macOS 用户账号和断网环境中完成首次配置、BGE `encode`、真实 RAG+KG 检索、MCP、网页、新题完整流程、备份与恢复；最终 `.tar.gz` 和 SHA-256 可复验。

### P1-4 缺少恢复流程

**处理口径：可由接手者继续；正式生产使用前应完成。**

证据：`backend/backup.py` 能生成包含 `data/questions`、`data/control`、`releases` 和 `backup-manifest.json` 的 `.tar.gz`，但 `scripts/` 与 `backend/` 中没有恢复脚本，也没有恢复测试。

影响：有备份不等于可恢复。误操作、升级失败或题库损坏后，无法证明可安全回滚。

建议：实现带预检、目标路径校验、恢复前再备份、临时目录解包、完整性检查和原子替换的恢复命令；不得直接覆盖未知目录。

验收条件：在副本上创建变更、备份、恢复并核对题目数、审计、控制文件和发布包；冻结基础设施和模型不受影响；恢复失败不破坏现有数据。

### P1-5 尚未完成一次 V2 端到端业务闭环

**处理口径：可由接手者继续；正式业务发布阻塞。**

当前 395 道题全部位于 `evidence_research`，`releases/` 为空；题库内没有 `evidence_candidates.jsonl`、`evidence_confirmation.json`、`analysis_versions.jsonl`、`final_checks.jsonl` 或 `decision.json`。

影响：版本门禁有单元测试，但尚无真实题从证据精选走到发布包的验收证据。

建议：修复真实检索后，在数据副本中选择一道人造或明确测试题，完成 Codex 和网页协作流程，不要直接用正式题库做不可逆试验。

验收条件：发布清单能够反查题面版本、证据确认版本、解析版本、最终核验版本、决定版本和审计记录；任一版本变化后旧批准不能再次发布。

## 4. 中优先级

### P2-1 新题准入存在两个追溯断点

**处理口径：可由接手者继续。**

当前代码：

- `needs_source_clarification` 建档后没有补附件或修复 intake 的 API/MCP。
- 重复判断选择 `merge` 时只保存自由文本理由，没有结构化 `merge_target_question_id`。

影响：待补题源无法沿正式入口继续推进；合并来源无法可靠反查到保留题。

处理决定：本次文档工程只记录问题，不新增设计。由接手开发者决定补全流程和字段迁移。

验收条件：待补题源可以在不丢失原档案与审计的前提下继续；合并记录具有可校验的目标题号。

### P2-2 Windows 与 macOS 依赖均无提交的精确锁文件

**处理口径：可由接手者继续。**

`backend/requirements.txt` 只有范围约束；当前 Windows `.venv` 的 `transformers 4.57.6` 由间接依赖解析得到，但没有被记录。`requirements-macos-arm64.lock` 尚不存在。

影响：同一安装命令在不同时间可能得到不同依赖组合，当前 BGE 失败难以稳定复现或修复。

建议：为 Windows 开发与 macOS arm64 分别生成经过真实检索验收的锁文件，并记录 Python 小版本、平台和 CPU 架构；构建脚本只使用已验收锁文件。

验收条件：两台干净环境按锁文件安装后，单元测试、模型 `encode` 和真实检索结果结构一致。

### P2-3 MCP 配置仍依赖开发机外部项目和绝对路径

**处理口径：可由接手者继续。**

正式版根目录没有 `.codex/config.toml`。当前 Windows 开发机把 `cams_workbench` 登记在 `D:\守正公司工作区\cams考试\.codex\config.toml`，并指向本机 Python 与正式版绝对路径。

影响：复制正式版目录后，接手者的 Codex 不会自动得到 MCP；现有配置也不可移植。

建议：交接时提供生成项目级配置的开发脚本或明确的手工步骤，配置应由接手机器生成，不应提交现有用户名和磁盘路径。

验收条件：接手者在自己的正式版项目中运行一次配置流程，重启 Codex 后能列出 MCP 工具并读取网页当前题；移动目录后能重新生成配置。

### P2-4 API 和存储层仍保留两套流程接口

**处理口径：可由接手者继续。**

`backend/api.py` 仍暴露 `ds-draft`、`codex-review`、`decision`、`evidence-review` 和 `draft-input`；`storage.py` 仍保留对应旧方法。V2 页面和 MCP 使用证据候选、解析版本、最终核验及 `workflow-decision`。

影响：维护者可能误用旧接口，形成 V2 页面看不到但旧 `question.status` 被修改的数据。当前测试已验证 V2 发布不会回退使用旧批准，但接口歧义仍存在。

决定：先统计是否还有真实调用者，确认无调用者后删除旧 DS 链路。删除前保持 Deprecated 标记，不再扩展；不要删除旧数据文件的读取和追溯能力。

验收条件：生产入口只有一套明确工作流；旧接口要么返回明确弃用提示，要么有单独的迁移测试和文档。

### P2-5 配置存在未生效字段

**处理口径：可由接手者继续。**

- `settings.example.toml` 的 `[workspace]`、`[server]`、`[codex]` 当前没有代码读取，只有 `[retrieval]` 生效。
- `RetrievalConfig.section_context_range` 被定义和校验，但没有参与算法。

影响：接手者可能把示例配置或参数快照误认为已经生效。

决定：`section_context_range` 不直接删除，由接手开发者先对照重构版脚本确认原始用途；其他未生效配置决定接入或删除前，应补测试和文档。

### P2-6 题号不能保证永不复用

**处理口径：可由接手者继续。**

题号分配在全局锁内扫描现存最大目录后加一，并发建档不会重复；但没有持久化序列。若人工删除最大编号题目目录，该编号可能再次分配。

影响：当前实现不能满足“删除后也永不复用”的严格承诺。

验收条件：要么实现不可回退的持久化序列并覆盖恢复场景，要么把禁止删除题目目录作为长期数据约束。

## 5. 低优先级

### P3-1 自动化测试未覆盖真实模型和完整浏览器流程

**处理口径：可由接手者继续。**

27 项测试覆盖锁、版本失效、题号分配、准入、证据去重、解析门禁、发布版本绑定、备份生成和教材页匹配；不覆盖真实 BGE 模型加载、MCP Desktop 连接或完整浏览器交互。

测试中会出现 MuPDF 对伪 PDF 的 `unknown keyword: 'qQq'` 警告，但用例仍通过；这是测试夹具警告，不代表真实教材 PDF 在本次运行中损坏。

建议验收条件：增加真实模型冒烟测试的显式可选标记，并使用浏览器自动化覆盖半屏布局、证据定位 5 秒高亮、未保存批注保护及网页/MCP 状态联动。

### P3-2 `backend/review/` 为空，模块边界与实现位置不一致

**处理口径：可由接手者继续。**

正式审核、人工决定和发布构建都在 `storage.py`，`backend/review/` 只有 `__init__.py`。这不影响当前行为，但会误导新开发者。

建议验收条件：在保持 `storage.py` 唯一写入边界的前提下，决定是删除空目录、补充说明，还是提取纯校验/发布组装逻辑；不要让新模块绕过存储层直接写文件。

### P3-3 macOS 运维能力仍未实现

**处理口径：可由接手者继续。**

macOS README 已按当前代码补充，但脚本仍没有停止服务、可靠端口身份检查、升级已有安装、失败回滚和恢复实现。运行时来源也尚未确定。

验收条件：从干净 M3 到运行、诊断、停止、升级、恢复和卸载均有可复现实现与测试，文档和脚本输出一致。

### P3-4 未使用模块需要接手者定去留

**处理口径：可由接手者继续。**

- `backend/infrastructure/catalog.py` 全仓无调用者，当前只读取教材 manifest 和 units。
- `backend/review/` 只有空包标记；审核和发布仍在 `storage.py`。

决定：`catalog.py` 标记为当前未使用，由接手者判断保留或删除；`review/` 暂保留为未来可能的纯校验/发布组装边界，本次不迁移代码。
