# 从技术文本提取业务流程图：跨领域文献综述及对 P7E 的启示

## 一、结论先行

现有文献没有证明一种“把整本规范一次交给 LLM，就能稳定得到完整且不漏桥接的流程图”的成熟方法。相反，业务流程、工业操作、医学指南、建筑规范和法律文本五类研究逐渐收敛到同一条技术路线：先定义或归纳目标语义，分阶段抽取节点与关系，再把结果映射为图或可执行规则，最后用结构约束、实例运行和人工专家复核验证。

`【LLM推理】` 对 P7E 而言，最合适的定位不是“自由生成流程图”，而是“P7C card 接口之间的高召回候选发现、节点级语义裁决、最小桥接节点生成、图约束校验和人工复核编排”。P7E 输出可以是新增 flow node 和 flow edge，但每个由模型补出的节点或边都必须显式标记 `llm_inferred`，并保存源 card、源节点、证据文本和推理摘要。

## 二、不同领域实际上在解决什么

| 领域 | 典型输入 | 中间语义 | 最终表示 | 对 P7E 的价值 |
|---|---|---|---|---|
| 业务流程 | 流程叙述 | Activity、Actor、Gateway、Condition、Flow、共指 | BPMN/流程图 | 最直接的节点与边骨架 |
| 工业/化学 | 实验步骤、操作规程 | 动作类型、对象、设备、温度/时间等参数 | action sequence/action graph | 强调动作槽位、顺序和可执行性 |
| 医学 | 临床指南、建议 | 适用条件、诊疗动作、优先级、规则 | GDL、Drools、FHIR 建议 | 强调适用性、形式化、执行验证和专家复核 |
| 建筑 | 规范条文、BIM 数据 | 对象、属性、比较符、阈值、例外、规则 | 本体、KG、RDF/IFC、合规规则 | 强调“文本语义—规则—数据”的分层映射 |
| 法律/监管 | 法条、裁判文书 | 主体、行为、模态、条件、例外、时间、制裁 | 元数据、三元组、KG | 补齐条件、例外、允许/必须等规范语义 |

## 三、直接证据

### 1. 流程抽取的核心不是找动词，而是恢复图结构

Friedrich 等（2011）已经把 NLP、指代消解和规则映射组合成 BPMN 生成管线，但在 47 组文本—模型对上也只能平均恢复约 77% 的模型内容。Bellan 等的综述进一步指出，十种既有方法在输入、输出和评价上高度异质，没有工具在全部流程元素上表现很好。

PET 数据集把流程抽取明确拆成节点和关系。节点包括 Activity、Actor、Activity Data、Further Specification、XOR/AND Gateway、Condition Specification；关系包括 Uses、Actor Performer、Actor Recipient、Further Specification、Same Gateway 和 Flow。其基线整体实体 F1 约 0.74、关系 F1 约 0.61，作者明确认为主要困难是召回不足，而非只要提高精确率。

这组证据直接回应了 P7E 的底线：“不能漏掉真实桥接”不能靠格式校验保证，因为格式正确的图仍然可以缺边。

### 2. LLM 有用，但必须被任务定义和输出结构约束

Neuberger 等（2024）把 LLM 任务拆为 mention 检测、实体归并、关系抽取，再由启发式算法生成流程模型。在三个数据集和八个 LLM 上，结构化提示相对既有方法带来最高约 8 个百分点的绝对 F1 提升。消融结果强调：定义是否具体、示例数量和格式约束强度会显著影响结果。

Carriero 等（2024）要求 LLM 按预定义本体，从无格式程序文本中抽取步骤、动作、对象、设备和时间信息，再生成程序知识图谱。研究同时指出，步骤切分本身具有主观性，不同人工标注也可能都合理，因此需要人工质量评价而不能假设唯一真值。

Dagdelen 等（2024）则证明，LLM 可以把句子或段落联合转换为实体、关系和 JSON 记录。共同证据是：LLM 最适合做受约束的语义映射，而不是无模式地自由画图。

### 3. 工业流程重视“动作+参数+可执行顺序”

Vaucher 等（2020）先定义化学操作类型及属性，再用规则系统生成大量预训练数据，以人工标注微调 Transformer，最终输出结构化动作序列。其测试集中 60.8% 的句子获得动作序列完全匹配，82.4% 的句子达到 75% 匹配。

ChemActor（2025）继续采用专用动作表示，但用通用 LLM 生成和筛选训练数据，降低人工标注成本。未能自动下载的 Ruehle（2025）更进一步：把超过 150 万条实验程序半自动标为 action graph，再生成可编辑 node graph 和 knowledge graph。这一路线说明，工业场景并不把“自然语言相邻”当成流程边，而要求动作、对象和参数在执行语义上兼容。

### 4. 医学指南强调形式化后的验证和复核队列

Nan 等（2020）采用翻译、解释、标注、抽取、形式化六步法，把 COVID-19 叙述性指南转成 27 个 archetype、18 条 GDL 规则及 Drools 规则，并用公开数据运行原型验证。这里的关键不是 PDF 格式是否合法，而是规则在实例上是否得到正确结果。

Lichtner 等（2023）进一步区分“建议是否适用于患者”和“建议是否已经实施”，并用 FHIR 表示指南建议。它说明条件触发、适用性和执行状态是不同语义，不应被压成一条模糊的 `precedes` 边。

Hsu 等（2025）虽然做的是指南建议分类而不是流程图抽取，但其质量控制非常有价值：GPT-4o 与 Gemini 各对 385 条建议重复 20 次；两模型准确率分别为 93.5% 和 92.7%；两模型一致的 341 项中仅 1 项偏离专家标签，并使人工复核量下降 88.6%。这为“模型一致则低风险通过，分歧则优先复核”提供了实证。

### 5. 建筑规范强调本体、映射和分层职责

Chen 等（2024）的管线包含四层：轻量领域本体、深度学习预分类、LLM 结构化抽取、BIM 合规检查。预分类不是最终判断，而是帮助 LLM 聚焦正确规则类型。Peng 与 Liu（2023）把规范条文形成 KG，再与 BIM 导出的 RDF 数据做映射和规则检查。

Beach 等（2015）明确区分三个语义上下文：目标领域语义、具体法规语义、待检查数据格式语义。Nawari（2019）也把规范转换、规则建模、数据标准和合规执行拆成模块。Farghaly 等（2022）则从 165 个事故案例和 31 份材料归纳安全本体，再映射到 IfcOWL，并用 SPARQL 检查语义一致性。

这些研究共同说明：图 schema 可以从样本归纳，但归纳完成后必须冻结成可校验的类型系统；否则无法可靠映射、查询和验证。

### 6. 法律文本补齐条件、例外和模态

Sleimi 等（2018）归纳并抽取 agent、action、modality、condition、constraint、exception、time、location、reference、sanction 等法律元数据。对 P7E 尤其重要的是 modality 与 exception：同样的动作可能是“必须”“可以”“禁止”或“仅在例外条件下”，它们不能用同一种前后关系表达。

Chen 等（2020）在中文法律文本上联合抽取实体和关系，三元组抽取 F1 达 0.836。它说明节点识别和边判断之间存在反馈，完全割裂的流水线会传播错误。

## 四、面向 P7E 的方法迁移

以下内容是依据上述文献与当前 P7C/P7E 约束形成的 `【LLM推理】`，不是任何单篇论文的原结论。

### 1. P7E 应采用五阶段管线

```text
P7C/P7D通过的cards
        |
        v
[1 接口标准化]
  同义词、共指、主体、对象、状态、条件、章节位置
        |
        v
[2 高召回候选生成]
  显式接口匹配 + 词汇/实体匹配 + 向量召回 + 邻近窗口 + 全局倒排
        |
        v
[3 LLM节点级语义裁决]
  判断源exit node是否能流向目标entry node
  必要时仅生成最少的condition/gateway/event/join flow node
        |
        v
[4 图约束与语义复检]
  端点、类型、条件完整性、可达性、环、重复边、分支/汇合一致性
        |
        v
[5 人工复核]
  所有llm_inferred节点；模型分歧；低置信；跨章远距离桥接；异常拓扑
```

这一路线兼顾“不能漏桥接”和全书规模。候选阶段追求召回，裁决阶段追求语义精度，图校验负责排除结构错误，人工复核负责模型无法证明的隐含语义。

### 2. 桥接必须落到节点级

建议每条桥接至少包含：

```json
{
  "source_card_id": "...",
  "source_node_id": "exit-node-id",
  "target_card_id": "...",
  "target_node_id": "entry-node-id",
  "relation_type": "flow_edge_type",
  "condition_refs": [],
  "bridge_node_ids": [],
  "derivation": "explicit|llm_inferred",
  "evidence_refs": [],
  "llm_reasoning_summary": "...",
  "confidence": 0.0,
  "review_status": "pending|approved|rejected"
}
```

`source_card -> target_card` 只能作为检索索引或汇总视图，不能成为最终流程事实。最终事实必须指明源 card 的哪个 exit node 与目标 card 的哪个 entry node 相连。

### 3. 新增 flow node 应遵守“最小补点”原则

可优先从样本开放编码以下候选类别，而不是立即写死完整枚举：

- `condition`：进入某条路径必须满足的状态；
- `gateway_xor`：互斥选择；
- `gateway_and_split` / `gateway_and_join`：并行分支与汇合；
- `trigger_event`：情境或事件触发；
- `wait_state`：等待外部结果或时间；
- `join/merge`：多条替代路径回到共同下游；
- `termination`：流程终止或拒绝继续。

每个新增节点必须满足三个条件：原有 card 的 exit/entry node 无法直接表达该语义；不补该节点会导致条件、分支或汇合信息丢失；可以指出支撑它的原文或明确标为 LLM 推理。纯粹为了让图更好看而增加的节点不应落库。

### 4. 用扎根理论形成 flow-edge schema

可在首批 30 至 50 个 section 上执行：

1. 开放编码：记录所有实际出现的桥接理由，不预设最终枚举；
2. 主轴编码：合并同义关系，分清时序、条件、因果、触发、数据依赖、角色移交、例外和汇合；
3. 选择编码：只保留能改变图执行语义、能稳定判断、能被下游消费的核心类型；
4. 反例检验：专门找无法归类或一条边需要多标签的案例；
5. 冻结 v1 schema：给每个关系写正例、反例、端点约束和必填字段；
6. 后续新类型进入变更队列，不允许模型即时发明生产枚举。

这与建筑安全本体从真实案例归纳概念、PET 用人工指南冻结注释体系的做法一致。

### 5. 全书规模不应全量两两调用 DS Pro

当前全书约 339 个 section、4,973 个 unit，预计 120 至 180 张 card。全量有向 card 对约为 14,280 至 32,220 个，还没有乘以每张 card 的多个入口/出口节点。逐对使用昂贵模型会把大量预算花在显然不相关的组合上。

`【LLM推理】` 应使用多路召回并集，保证任何一路命中都进入候选集：

- 接口的主体、对象、状态、动作直接匹配；
- 同义词、缩写、共指和术语本体匹配；
- BM25/倒排词项召回；
- embedding 语义召回；
- 同章、邻章和原文引用窗口；
- 全局“产出状态 -> 消费状态”索引；
- 已知人工桥接的相似案例召回。

DS Pro 只处理候选边的语义裁决和复杂桥接补点。为了守住召回率，应对每个 source exit 至少保留 top-k 语义候选，并用一小批人工金标准调 k 和阈值，而不是凭感觉设定。

### 6. 质量门槛应从“格式正确”升级为“图事实正确”

建议 P7E 试跑同时报告：

- 真实桥接召回率：第一优先指标；
- 桥接精确率：人工复核通过的候选占比；
- 节点级端点准确率：card 对找对但节点找错仍算错；
- 条件/例外完整率；
- 幻觉节点率：无原文或无法接受的 LLM 补点占比；
- 拓扑可达率：从入口到预期出口是否存在路径；
- 人工复核负担：每 100 张 card 需要复核多少边/节点；
- 分歧率和复核收益：重复推理或双模型分歧是否能有效定位错误。

P7C 的格式校验不能替代这些指标。P7D 可以继续负责 card 内部质量，而 P7E 必须对跨 card 的图语义和完整性负责。

## 五、建议的下一步试验

`【LLM推理】` 在第一章前 30 个 section 上先做 schema 发现和提示校准，再扩到前 50 个 section。试验应保留完整候选集，不只保留模型最终接受的边，以便人工检查漏召回发生在候选阶段还是语义裁决阶段。

最小试验产物应包括：

1. P7C/P7D card 与节点清单；
2. 多路候选边及每路召回原因；
3. DS Pro 对候选边的节点级裁决结果；
4. 所有 `llm_inferred` flow node；
5. 机器图校验报告；
6. 人工复核表；
7. 最终 Draw.io 图及其可追溯 JSON。

只有当 30-section 金标准上“真实桥接召回率”达到可接受水平，才应扩大到 50 section 和全书。否则，全书运行只会放大漏边而不会暴露漏边原因。
