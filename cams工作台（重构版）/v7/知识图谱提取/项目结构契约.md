# v7 知识图谱提取项目结构契约

本文定义 `v7/知识图谱提取` 的目录职责和文件归属规则。后续新增、迁移、删除文件时，以本文作为裁决依据。

## 总体原则

1. 每个 phase 自包含：该阶段的 README、契约、脚本、输入样例、输出、报告、预览、prompt 应放在自己的 phase 目录下。
2. 根目录只放导航、状态、跨阶段契约和治理文档，不放阶段脚本和阶段产物。
3. `lib` 只放跨阶段共享代码，不放产物、不放一次性脚本。
4. `archive` 只放历史快照和废弃材料，不作为当前执行入口。
5. 当前 KG 默认产物路径是 `phases/*`，不是旧 `work/kg`。

## 根目录职责

根目录用于说明“这个项目是什么、现在到哪里、按什么规则维护”。

允许放置：

- `README.md`：入口导航，只写稳定定义、当前状态和关键入口。
- `项目结构契约.md`：本文件，定义目录归属规则。
- `kg各环节职责与概况.md`：跨阶段职责概览。
- 全局治理类文档：例如规则治理、数据契约、全流程说明。

禁止放置：

- 新增 phase 脚本。
- phase 输出、报告、预览、LLM 响应。
- 一次性修复脚本或实验脚本。
- 新生成的大型中间产物。

## `phases/` 职责

`phases/` 是当前 KG 主执行结构。每个 phase 应尽量自包含。

推荐结构：

```text
phases/phaseXX_name/
├── README.md
├── contract.md
├── scripts/
├── inputs/
├── outputs/
├── reports/
├── previews/
├── prompts/
└── review_packets/
```

不是每个 phase 都必须拥有全部子目录；只创建实际需要的目录。

放置规则：

- `scripts/`：该 phase 的执行脚本、校验脚本、渲染脚本。
- `inputs/`：该 phase 专属输入、人工决策输入、样例输入。
- `outputs/`：机器可读正式产物，例如 JSON/JSONL。
- `reports/`：审计报告、统计报告、验收报告。
- `previews/`：给人工阅读的 Markdown/表格预览。
- `prompts/`：该 phase 专属 LLM prompt 和 prompt version。
- `review_packets/`：人工审核包、决策包、建议包。

跨 phase 共享的脚本不能随便放在某个 phase 下；只有被多个 phase 复用且无业务副作用的代码，才进入 `lib`。

## `lib/` 职责

`lib/` 是跨 phase 公共库，当前核心文件是 `lib/kg_common.py`。

允许放置：

- 路径常量和兼容映射。
- JSON/JSONL/Markdown I/O 工具。
- 跨 phase 共享的枚举、schema 常量、风险标记集合。
- 无副作用的排序、分组、统计、格式化函数。

禁止放置：

- 任何 phase 独有脚本。
- 会在 import 时执行 pipeline 的代码。
- 会在 import 时读写大文件、调用模型或修改产物的代码。
- prompt、报告、预览、LLM 响应、人工审核包。

新增脚本如果只服务一个 phase，应放在该 phase 的 `scripts/`。只有当同一逻辑被两个及以上 phase 复用，并且抽出来能减少重复和路径混乱时，才进入 `lib`。

## `config/` 职责

`config/` 放跨阶段稳定配置或人工决策数据。

允许放置：

- 人工确认的结构决策表。
- 跨 phase 共用的阈值、白名单、黑名单、规则配置。
- 不属于单一 phase 的全局配置。

如果配置只服务某个 phase，应优先放到该 phase 的 `inputs/` 或 `config/` 子目录，不放全局 `config/`。

## `archive/` 职责

`archive/` 放历史材料和废弃入口。

允许放置：

- 旧 README、旧迁移计划、旧长文档。
- 旧 `work/kg` 的归档快照。
- 已被新 phase 目录替代的旧脚本、旧产物、旧报告。

使用规则：

- 当前 pipeline 不应默认读取 `archive`。
- 如需兼容读取，必须显式通过 `LEGACY_KG_WORK_DIR` 或明确路径访问。
- 归档材料不再作为当前执行入口；要恢复使用，必须迁回对应 phase 并更新契约。

## `work/` 职责

根目录 `work/` 用于 P7 流程型 KG 的运行时产物和缓存。不同于旧 `work/kg`（已归档），当前 `work/` 是活跃工作区。

规则：

- P7 阶段产物可写入 `work/` 作为中间工作区。
- 稳定产物应最终进入对应 phase 的 `outputs/`。
- 无需保留的临时缓存不纳入版本控制。

## 脚本归属规则

脚本按“谁负责、产物归谁、失败归谁排查”来放置。

- 只服务一个 phase：放该 phase 的 `scripts/`。
- 服务多个 phase，但只是工具函数：抽到 `lib/`。
- 服务多个 phase，且本身是流程入口：放到最上游负责调度的 phase，并在 README 中说明调用范围。
- 废弃但需要留痕：放 `archive/`，不要留在当前执行路径。

禁止新增顶层 `scripts/`。如果未来确实需要总调度入口，应先在本文中新增“orchestration”目录规则。

## 产物归属规则

每个产物必须能回答三个问题：

1. 它由哪个 phase 生成？
2. 它供哪个后续 phase 使用？
3. 它是机器读产物、人工读报告，还是审核预览？

对应放置：

- 机器读产物：`phaseXX/outputs/`
- 统计和审计报告：`phaseXX/reports/`
- 人工阅读预览：`phaseXX/previews/`
- 人工审核包：`phaseXX/review_packets/`
- LLM prompt：`phaseXX/prompts/`
- 人工决策输入：优先 `phaseXX/inputs/`，跨阶段稳定后再提升到根 `config/`

## import 与依赖规则

- phase 脚本可以 import `lib/kg_common.py`。
- phase 脚本不应 import 另一个 phase 的脚本；跨 phase 复用逻辑应抽到 `lib`。
- phase 可以读取前置 phase 的 `outputs/`，但要在 README 或 contract 中写明输入路径。
- 后置 phase 不应反向修改前置 phase 的产物；需要修正时，通过 overlay、decision、review packet 或重新运行前置 phase 生成新版本。

## 维护口径

当结构和现实冲突时，优先处理顺序如下：

1. 先判断文件是否仍是当前执行链路必需。
2. 必需文件迁到对应 phase 或 `lib`。
3. 非必需但有追溯价值的文件进 `archive`。
4. 无追溯价值的临时文件删除。
5. 修改结构后，同步更新本契约和相关 README。
