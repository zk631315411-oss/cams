# 考点确认落地计划

## 1. 项目目标

把当前“教材句卡、题库、答疑记录、图谱”转化为教研可用的“考点确认工作流”。

教研希望打开教材原文时可以直接判断：

- 哪些原文句子或概念是考试考点
- 每个考点对应哪些题目和学生答疑
- 哪些考点只是 AI 候选，哪些已经由教研确认
- 题目、答疑、教材证据之间的关系是否可靠

本项目不把 `cards_ch2.json` 直接视为考点。`cards_ch2.json` 只是教材句卡/原文证据句抽取结果。只有进入新增考点数据层并经过状态标记的数据，才可以在界面中称为“考点”。

## 4. 生成候选考点的实践流程

### 4.1 第一阶段只做 37 条答疑试点

原因：

- 答疑记录代表真实学生困惑
- 更容易验证“考点是否有教学价值”
- 工作量可控

每条答疑生成一条或多条候选考点，字段包括：

- 学生问题
- 绑定题目
- 题目正确答案
- 主考点候选
- 学生误区
- 候选教材句卡
- 反推理由
- 状态：`ai_candidate`

### 4.2 候选生成逻辑

对每条答疑：

1. 读取学生问题和教研回答
2. 找到绑定题目
3. 分析题干和正确答案
4. 判断学生到底卡在哪里
5. 从教材句卡中召回候选原文证据
6. 生成候选考点
7. 标记为 `ai_candidate`

`question_card_map.json` 只允许参与第 5 步召回，不允许直接写入结论。

### 4.3 第二阶段扩展到 179 道题

37 条答疑试点通过后，再扩展到全部题库。

对每道题生成：

- 主考点候选
- 题目考法
- 候选教材句卡
- 是否有学生答疑
- 是否需要选项级解析

## 6. 验收标准

### 6.1 数据验收

第一阶段完成时必须满足：

- 已创建 `exam_points_ch2.json`
- 37 条答疑均至少生成 1 条候选考点，或明确标记为“无法生成，需人工处理”
- 每条候选考点必须包含：
  - `id`
  - `title`
  - `status`
  - `type`
  - `source_card_ids`
  - `question_ids`
  - `qa_ids`
  - `reason`
- 不允许把 `cards_ch2.json` 中的所有句卡直接批量标为考点
- `question_card_map.json` 只能作为候选参考，不得作为确认依据

### 6.2 前端验收

页面应满足：

- 原文中能区分教材句卡、AI 候选考点、教研确认考点
- 点击候选考点能看到题目、答疑、教材证据和反推理由
- 粗粒度映射必须明确显示“仅供参考”
- 教研可以对候选考点做确认、否定、改名、合并、拆分等反馈操作
- 教研反馈可以导出为 JSON
- 没有数据的字段必须显示占位文案，例如“待教研确认”“待绑定”“待补充”

### 6.3 教研体验验收

至少抽查 10 条答疑候选考点，教研应能判断：

- 这个候选考点是否真的值得作为考试考点
- 关联教材原文是否能支撑该考点
- 关联题目是否合理
- 学生误区描述是否有助于后续讲解

通过标准：

- 抽查样本中，教研认为“可确认或小修后可确认”的候选考点不少于 70%
- 教研能明确指出不合理候选的原因，并可通过反馈模块记录

### 6.4 技术验收

- 所有新增 JSON 文件必须能被 `JSON.parse` 正常解析
- 前端 JS 必须通过 `node --check`
- 页面加载时不能因为缺少考点数据而报错
- `cards_ch2.json` 新结构必须被前端兼容读取

## 12. 数据 Schema 细则

### 12.1 `exam_points_ch2.json` 顶层字段

必填：

```json
{
  "version": "0.1",
  "asset_note": "说明文字",
  "generated_at": "2026-06-06T00:00:00+08:00",
  "source_scope": "qa_37",
  "exam_points": []
}
```

### 12.2 `exam_points[]` 必填字段

每条必须包含：

```json
{
  "id": "ep_2_1_001",
  "title": "考点标题",
  "status": "ai_candidate",
  "type": "待分类",
  "source_card_ids": [],
  "question_ids": [],
  "qa_ids": [],
  "student_confusion": "",
  "reason": "",
  "teacher_note": "",
  "created_from": "qa",
  "confidence": "low",
  "needs": [],
  "updated_at": "2026-06-06"
}
```

字段约束：

- `id` 必须唯一，格式：`ep_2_x_数字`，例如 `ep_2_4_003`。
- `status` 必须来自状态枚举。
- `type` 必须来自考点类型枚举。
- `source_card_ids` 中的 ID 必须存在于 `cards_ch2.json`。
- `question_ids` 中的 ID 必须存在于 `questions.json`。
- `qa_ids` 中的 ID 必须存在于 `qa.json`。
- `reason` 不能为空，且必须说明为什么从题目或答疑反推出该考点。
- `confidence` 只能是 `high`、`medium`、`low`。
- 如果没有教材证据，`source_card_ids` 可以为空，但 `status` 必须是 `needs_evidence` 或 `needs_manual`。

## 13. 候选考点质量标准

- 标题不是题干原文。
- 标题不是“为什么选 A”这类学生问题。
- 至少能解释一个题目的正确答案或一个学生误区。
- 至少有一个来源：题目、答疑、教材证据三者之一。
- 如果称为 `ai_candidate`，必须有 `reason`。
- 如果没有 `source_card_ids`，必须明确写入 `needs_evidence`。

优先级判断：

- 有题目 + 有答疑 + 有教材证据：高优先级
- 有题目 + 有教材证据：中优先级
- 只有题目，无教材证据：低优先级，需人工处理

### 18.3 status 枚举最终列表

最终状态共 8 个：

- `ai_candidate`：AI 候选，待教研确认。
- `confirmed`：教研确认是考点。
- `rejected`：教研确认不是考点。
- `needs_merge`：候选成立，但应合并到其他考点。
- `needs_split`：候选过大或混杂，需要拆成多个考点。
- `needs_evidence`：有候选考点判断，但缺少可靠教材句卡证据。
- `needs_question_binding`：有候选考点和教材证据，但缺少可靠题目绑定。
- `needs_manual`：自动流程无法判断，需要人工处理。

`needs_manual` 与 `needs_evidence` 的区别：

- `needs_evidence`：已经能判断一个候选考点大致存在，但当前找不到足够好的教材原文证据。
- `needs_manual`：连候选考点本身都无法可靠生成，或答疑/题目数据异常导致无法判断。

示例：

- 学生问“为什么贸易洗钱资金从塞浦路斯到英国选 B”，能判断是“贸易洗钱资金流向判断”，但没找到教材句卡：`needs_evidence`。
- 答疑绑定题目缺失、题干无法读取、答案和选项严重不一致：`needs_manual`。
