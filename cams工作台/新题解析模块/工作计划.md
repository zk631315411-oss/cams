# 新题解析模块工作计划

创建日期：2026-06-13

## 目标定位

把现有“新题解析”页面从前端 demo 升级为一个真实可用的单题版四角色法模块：

```text
整段粘贴新题
→ 在线运行单题版四角色法
→ 生成 AI 参考答案和选项解析草稿
→ 展示四角色过程，方便教研观察和复核
→ 保存草稿 JSON
→ 暂不写入正式题库
```

该模块的定位是“AI 辅助生成可复核的新题解析草稿”，不是自动定稿工具。

## 工作区结构

```text
新题解析模块/
  api/                  本地接口服务
  pipeline/             单题四角色法流程代码
  prompts/              LLM 提示词
  outputs/
    drafts/             新题解析草稿 JSON
  logs/                 运行日志和调试记录
  tests/                小样本测试用例
  docs/                 设计文档、评测记录、问题清单
  工作计划.md
```

## 功能边界

第一版支持：

- 老师整段粘贴新题文本。
- 新题可以没有标准答案，由 AI 生成“AI 参考答案”。
- 证据检索默认面向全书，但最终证据只允许来自教材原文、术语表等一手教材材料。
- 第一版应沿用原四角色法的隔离原则：旧解析、学生答疑、已有考点不进入 LLM 主流程。
- 若后续确实引入已有解析或教研提示，也只能作为显式开启的 `retrieval_only` 检索提示，且必须在过程可视化中标出，不能作为教材依据。
- 结果保存为草稿 JSON，但暂不进入正式题库。
- 输出结构尽量贴近现有题目选项证据结构，方便前端复用。
- 四角色法的各环节尽量可视化，让人能看到中间内容。

第一版暂不做：

- 正式入库。
- 批量新题处理。
- 教研反馈闭环。
- 云端部署。
- 复杂历史草稿管理。

## 四角色法流程

### 1. 题目拆解

输入：老师粘贴的整段题目文本。

处理：

- 识别题干。
- 识别 A/B/C/D 选项。
- 识别原文中是否带有答案或解析。
- 提取关键词。
- 判断题型。
- 记录拆解警告。

输出示例：

```json
{
  "stem": "...",
  "options": {
    "A": "...",
    "B": "...",
    "C": "...",
    "D": "..."
  },
  "detected_answer": "",
  "question_type": "single_choice",
  "keywords": ["...", "..."],
  "parse_warnings": []
}
```

前端可视化：

- 题干
- 选项
- 识别到的答案
- 关键词
- 拆解警告

### 2. 证据检索

输入：题目拆解结果。

一手证据池：

- 教材句卡 `cards_v6_sentence.json`
- 教材章节/术语表相关产物

辅助召回资产：

- KG sections / edges / card_section_map
- card_relations
- 句卡相邻关系
- 可选的教研解析提示，仅限 `retrieval_only`

边界规则：

- 最终引用的 `evidence_cards` 只能来自一手证据池。
- 辅助召回资产只用于找教材句卡，不能直接进入最终证据。
- 第一版不把已有考点、旧题解析、学生答疑送入 LLM。
- 如果后续引入已有解析或教研提示，也必须显式标注为“检索提示”，并继续回溯到教材原文卡。

第一版技术路线：

- 题目和选项进入“检索规划员”，由 LLM 把每个选项改写成可检索的教材证据需求。
- 通过 card-level BGE、BM25、精确短语、相邻句卡、关系扩展等路线召回教材句卡。
- 对召回到的教材原文做合并、去重和加权排序。
- 裁判 LLM 只能看到题目、选项、检索规划和候选教材句卡。
- 新题没有标准答案时，采用盲判变体：输出 `AI 参考答案` 和置信度，而不是沿用标准答案控制 judgement 的正式批处理逻辑。

输出示例：

```json
{
  "candidates": [
    {
      "source_type": "textbook_card",
      "card_id": "v6s_...",
      "quote": "...",
      "chapter_path": "...",
      "score": 18,
      "matched_terms": ["..."],
      "used_in_final": true
    }
  ]
}
```

前端可视化：

- 教材原文 1 / 2 / 3
- 原文内容
- 来源章节
- 命中原因
- 是否被最终采用

老师界面不直接暴露 `v6s_...`，但 JSON 内保留内部 ID。

### 3. 答案判断

输入：题目拆解结果 + 候选证据。

LLM 任务：

- 基于给定证据判断 AI 参考答案。
- 证据不足时必须输出“不确定 / 需教研确认”。
- 不允许凭空编造教材依据。

输出示例：

```json
{
  "ai_answer": "B",
  "confidence": "medium",
  "reasoning_summary": "...",
  "uncertainties": ["..."],
  "evidence_refs": ["v6s_..."],
  "needs_teacher_review": true
}
```

前端可视化：

- AI 参考答案
- 置信度
- 判断理由
- 不确定点
- 是否需要教研复核

### 4. 选项解析

输入：题目拆解结果 + 答案判断 + 候选证据。

输出尽量贴近现有 `question_option_evidence` 结构：

```json
{
  "options": [
    {
      "option": "A",
      "judgement": "wrong",
      "explanation": "...",
      "evidence_status": "direct",
      "evidence_cards": [
        {
          "card_id": "v6s_...",
          "quote": "..."
        }
      ],
      "common_trap": "..."
    }
  ]
}
```

前端可视化：

- 每个选项的对错判断
- 每个选项的解析草稿
- 对应教材原文
- 证据强弱：直接依据 / 间接依据 / 依据不足
- 易错点

### 5. 质量校验

校验内容：

- 题干是否为空。
- 选项是否完整。
- AI 答案是否在选项范围内。
- 每个选项是否有解析。
- 引用的 `card_id` 是否真实存在。
- 引用内容是否来自检索候选。
- 是否存在无依据强判断。
- 是否需要教研复核。

输出示例：

```json
{
  "validation_status": "needs_review",
  "checks": [
    {
      "name": "引用句卡存在",
      "status": "pass"
    },
    {
      "name": "每个选项均有解析",
      "status": "pass"
    },
    {
      "name": "C 选项依据较弱",
      "status": "warning"
    }
  ]
}
```

前端可视化：

- 通过项
- 警告项
- 失败项
- 总体结论

## 草稿 JSON 结构

每次运行保存一个草稿文件：

```text
outputs/drafts/nq_YYYYMMDD_HHMMSS_xxxx.json
```

建议结构：

```json
{
  "draft_id": "nq_20260613_153012_xxxx",
  "created_at": "2026-06-13T15:30:12+08:00",
  "status": "draft",
  "raw_input": "...",
  "pipeline": {
    "parse_question": {},
    "retrieve_evidence": {},
    "judge_answer": {},
    "explain_options": {},
    "validate": {}
  },
  "final": {
    "ai_answer": "B",
    "confidence": "medium",
    "option_explanations": [],
    "evidence_cards": [],
    "needs_teacher_review": true
  }
}
```

## API 设计

第一版只需要一个核心接口：

```text
POST /api/new-question/analyze
```

请求：

```json
{
  "text": "整段新题文本"
}
```

响应：

```json
{
  "draft_id": "...",
  "pipeline": {},
  "final": {}
}
```

后续可以补充：

```text
GET /api/new-question/drafts
GET /api/new-question/drafts/:draft_id
```

## 前端展示设计

现有“新题解析”页改成：

```text
输入区
  整段粘贴新题
  生成解析草稿

结果区
  解析草稿
  四角色过程
```

解析草稿默认展示：

- AI 参考答案
- 置信度
- 选项解析
- 教材依据
- 需要复核提示

四角色过程可折叠展示：

- 题目拆解
- 证据检索
- 答案判断
- 选项解析
- 质量校验

原则：

- 日常使用不复杂。
- 需要复核时能看到中间过程。
- 不把内部句卡 ID 暴露给老师界面。
- 所有“答案”都称为“AI 参考答案”，避免误导成定稿。

## 提示词文件规划

```text
prompts/
  01_parse_question.md
  02_judge_answer.md
  03_explain_options.md
  04_validate.md
```

提示词共同约束：

- 只能基于给定题目和给定证据作答。
- 证据不足必须标注。
- 输出必须是 JSON。
- 不允许编造 `card_id`。
- 不允许把弱证据写成强结论。

## 质量评价标准

第一版达标条件：

- 可以从整段粘贴文本中稳定拆出题干和选项。
- 至少能返回若干候选教材依据。
- AI 参考答案和选项解析能基于候选证据生成。
- 每个最终引用的证据都能回到真实教材句卡。
- 过程可视化能帮助判断错误发生在哪一环。
- 结果能保存为草稿 JSON。
- 不影响现有正式题库和教材展示。

## 主要风险

### 检索错

表现：LLM 拿到的证据本身不相关。

应对：

- 展示候选证据和命中原因。
- 保留未采用证据。
- 小样本评测先看检索质量。

### 弱证据被说成强结论

表现：解析看起来很顺，但教材依据不足。

应对：

- 强制输出 `evidence_status`。
- 校验“无依据强判断”。
- 前端标注“依据不足 / 需复核”。

### 拆题失败

表现：选项漏掉、题干截断、答案识别错。

应对：

- 题目拆解环节可视化。
- 保存 `parse_warnings`。
- 必要时前端提示老师修正输入。

### 前端复杂化

表现：信息太多，老师反而看不清。

应对：

- 默认显示最终草稿。
- 四角色过程折叠展示。
- 内部 ID 不直接显示。
